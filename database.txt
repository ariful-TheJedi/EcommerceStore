# E-commerce database schema

Let's consolidate the decisions into one practical schema for your Bangladesh e-commerce store. I'll use PostgreSQL data types, keep `users` and `customers` separate, and use separate `product_images` and user avatar storage rather than forcing every file into a universal media system.

The goal is a database that is standard, maintainable, and ready for your initial store without introducing unnecessary complexity.

## 1. Table list

| No. | Table                       | Purpose                                    |
| --- | --------------------------- | ------------------------------------------ |
| 1   | `users`                     | Login accounts and authentication          |
| 2   | `customers`                 | Customer-specific information              |
| 3   | `password_reset_tokens`     | Password reset workflow                    |
| 4   | `email_verification_tokens` | Email verification                         |
| 5   | `addresses`                 | Customer delivery and billing addresses    |
| 6   | `categories`                | Categories and subcategories               |
| 7   | `products`                  | Main product information                   |
| 8   | `product_variants`          | Purchasable options such as size and color |
| 9   | `product_images`            | Product and variant images                 |
| 10  | `carts`                     | Customer shopping carts                    |
| 11  | `cart_items`                | Products and quantities in carts           |
| 12  | `orders`                    | Order details and totals                   |
| 13  | `order_items`               | Purchased product snapshots                |
| 14  | `payments`                  | Payment attempts and payment status        |
| 15  | `inventory_transactions`    | Stock movement history                     |
| 16  | `coupons`                   | Discount codes                             |

This is a sensible starting point. You don't need separate tables for every possible color or size: each purchasable combination will be a row in `product_variants`.

## 2. Column definitions, data types, and constraints

Conventions used throughout:

- `BIGINT GENERATED ALWAYS AS IDENTITY` — auto-generated numeric primary key.
- `TIMESTAMPTZ` — timestamp stored with timezone awareness.
- `NUMERIC(12,2)` — monetary values; avoid floating-point types for money.
- `JSONB` — flexible structured data, useful for variant attributes.
- `FK` means foreign key; `UNIQUE` prevents duplicates; `CHECK` validates allowed values.
- Unless otherwise stated, tables with `created_at` and `updated_at` use `TIMESTAMPTZ NOT NULL DEFAULT NOW()`.

### A. Users, customers, and addresses

#### 1. `users`

Stores login accounts for customers and administrators.

| Column              | Data type    | Constraint                                                                    |
| ------------------- | ------------ | ----------------------------------------------------------------------------- |
| `id`                | BIGINT       | PK, identity                                                                  |
| `name`              | VARCHAR(150) | NOT NULL                                                                      |
| `email`             | VARCHAR(255) | NOT NULL, UNIQUE                                                              |
| `phone`             | VARCHAR(20)  | NULL, UNIQUE                                                                  |
| `password`          | VARCHAR(255) | NOT NULL; store a password hash                                               |
| `role`              | VARCHAR(20)  | NOT NULL, DEFAULT `'customer'`, CHECK role is `customer`, `admin`, or `staff` |
| `avatar_path`       | VARCHAR(500) | NULL                                                                          |
| `email_verified_at` | TIMESTAMPTZ  | NULL                                                                          |
| `is_active`         | BOOLEAN      | NOT NULL, DEFAULT TRUE                                                        |
| `created_at`        | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()                                                       |
| `updated_at`        | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()                                                       |

#### 2. `customers`

Stores customer-specific information separately from authentication.

| Column          | Data type   | Constraint                        |
| --------------- | ----------- | --------------------------------- |
| `id`            | BIGINT      | PK, identity                      |
| `user_id`       | BIGINT      | NOT NULL, UNIQUE, FK → `users.id` |
| `date_of_birth` | DATE        | NULL                              |
| `created_at`    | TIMESTAMPTZ | NOT NULL, DEFAULT NOW()           |
| `updated_at`    | TIMESTAMPTZ | NOT NULL, DEFAULT NOW()           |

A customer has one user account, and a user account has at most one customer profile. Admin/staff accounts do not need customer profiles.

#### 3. `password_reset_tokens`

| Column       | Data type    | Constraint |
| ------------ | ------------ | ---------- |
| `email`      | VARCHAR(255) | PK         |
| `token`      | VARCHAR(255) | NOT NULL   |
| `created_at` | TIMESTAMPTZ  | NULL       |

Store a securely generated, hashed reset token where supported. Expiry and one-time use should be enforced by the reset workflow; expired records should be cleaned up.

#### 4. `email_verification_tokens`

| Column       | Data type    | Constraint                        |
| ------------ | ------------ | --------------------------------- |
| `id`         | BIGINT       | PK, identity                      |
| `user_id`    | BIGINT       | NOT NULL, FK → `users.id`, UNIQUE |
| `token_hash` | VARCHAR(255) | NOT NULL, UNIQUE                  |
| `expires_at` | TIMESTAMPTZ  | NOT NULL                          |
| `created_at` | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()           |

Delete or invalidate the token after successful verification. If you use Laravel's built-in email verification and password-reset mechanisms, adapt these tables to Laravel's conventions rather than creating duplicate mechanisms.

#### 5. `addresses`

A customer can have multiple delivery or billing addresses.

| Column           | Data type    | Constraint                    |
| ---------------- | ------------ | ----------------------------- |
| `id`             | BIGINT       | PK, identity                  |
| `customer_id`    | BIGINT       | NOT NULL, FK → `customers.id` |
| `label`          | VARCHAR(50)  | NULL, e.g. Home or Office     |
| `recipient_name` | VARCHAR(150) | NOT NULL                      |
| `phone`          | VARCHAR(20)  | NOT NULL                      |
| `address_line1`  | VARCHAR(255) | NOT NULL                      |
| `address_line2`  | VARCHAR(255) | NULL                          |
| `area`           | VARCHAR(100) | NULL                          |
| `city`           | VARCHAR(100) | NOT NULL                      |
| `district`       | VARCHAR(100) | NULL                          |
| `postal_code`    | VARCHAR(20)  | NULL                          |
| `country_code`   | CHAR(2)      | NOT NULL, DEFAULT `'BD'`      |
| `is_default`     | BOOLEAN      | NOT NULL, DEFAULT FALSE       |
| `created_at`     | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()       |
| `updated_at`     | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()       |

Add an index on `customer_id`. If you need to guarantee one default address per customer, use a partial unique index on `customer_id` where `is_default = TRUE`.

### B. Categories and product catalog

#### 6. `categories`

Supports nested categories and subcategories using a self-referencing relationship.

| Column        | Data type    | Constraint                                     |
| ------------- | ------------ | ---------------------------------------------- |
| `id`          | BIGINT       | PK, identity                                   |
| `parent_id`   | BIGINT       | NULL, FK → `categories.id`, ON DELETE RESTRICT |
| `name`        | VARCHAR(150) | NOT NULL                                       |
| `slug`        | VARCHAR(180) | NOT NULL, UNIQUE                               |
| `description` | TEXT         | NULL                                           |
| `image_path`  | VARCHAR(500) | NULL                                           |
| `is_active`   | BOOLEAN      | NOT NULL, DEFAULT TRUE                         |
| `sort_order`  | INTEGER      | NOT NULL, DEFAULT 0                            |
| `created_at`  | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()                        |
| `updated_at`  | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()                        |

A `parent_id` of `NULL` means a top-level category. For example, Home Organization → Storage Boxes.

#### 7. `products`

Stores information common to all variants of a product.

| Column        | Data type    | Constraint                                                       |
| ------------- | ------------ | ---------------------------------------------------------------- |
| `id`          | BIGINT       | PK, identity                                                     |
| `category_id` | BIGINT       | NULL, FK → `categories.id`, ON DELETE SET NULL                   |
| `name`        | VARCHAR(200) | NOT NULL                                                         |
| `slug`        | VARCHAR(220) | NOT NULL, UNIQUE                                                 |
| `description` | TEXT         | NULL                                                             |
| `status`      | VARCHAR(20)  | NOT NULL, DEFAULT `'draft'`, CHECK `draft`, `active`, `archived` |
| `created_at`  | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()                                          |
| `updated_at`  | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()                                          |

Keep prices and stock on `product_variants`, because different variants may have different prices and quantities.

#### 8. `product_variants`

Each row represents one purchasable combination, such as a red 500 ml bottle.

| Column             | Data type     | Constraint                                             |
| ------------------ | ------------- | ------------------------------------------------------ |
| `id`               | BIGINT        | PK, identity                                           |
| `product_id`       | BIGINT        | NOT NULL, FK → `products.id`, ON DELETE RESTRICT       |
| `sku`              | VARCHAR(100)  | NOT NULL, UNIQUE                                       |
| `attributes`       | JSONB         | NOT NULL, DEFAULT `'{}'`, CHECK value is a JSON object |
| `price`            | NUMERIC(12,2) | NOT NULL, CHECK `price >= 0`                           |
| `compare_at_price` | NUMERIC(12,2) | NULL, CHECK `compare_at_price >= 0`                    |
| `stock_quantity`   | INTEGER       | NOT NULL, DEFAULT 0, CHECK `stock_quantity >= 0`       |
| `is_active`        | BOOLEAN       | NOT NULL, DEFAULT TRUE                                 |
| `created_at`       | TIMESTAMPTZ   | NOT NULL, DEFAULT NOW()                                |
| `updated_at`       | TIMESTAMPTZ   | NOT NULL, DEFAULT NOW()                                |

Add `UNIQUE (product_id, id)` to support the composite foreign key used by `product_images`.

Example `attributes` value:

`{"color": "Red", "size": "500ml"}`

This lets you support different attribute combinations without creating separate color, size, or shape tables at the beginning. Add attribute-management tables later if you need controlled options and advanced filtering.

#### 9. `product_images`

This is a purpose-specific table for product images. It references files through their paths, without requiring a universal `media` table.

| Column       | Data type    | Constraint                   |
| ------------ | ------------ | ---------------------------- |
| `id`         | BIGINT       | PK, identity                 |
| `product_id` | BIGINT       | NOT NULL, FK → `products.id` |
| `variant_id` | BIGINT       | NULL                         |
| `image_path` | VARCHAR(500) | NOT NULL                     |
| `alt_text`   | VARCHAR(255) | NULL                         |
| `is_primary` | BOOLEAN      | NOT NULL, DEFAULT FALSE      |
| `sort_order` | INTEGER      | NOT NULL, DEFAULT 0          |
| `created_at` | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()      |

Important variant constraint: add a composite FK `(product_id, variant_id)` → `product_variants(product_id, id)`. This ensures that a variant-specific image belongs to the same product named in the row. When `variant_id` is `NULL`, the image is a general product image.

Add a partial unique index on `product_id` where `is_primary = TRUE` to allow at most one primary image per product. If you need one primary image per variant as well, implement that rule separately.

### C. Optional product tags

These two tables are useful if you want labels such as `bestseller`, `new-arrival`, or `eco-friendly`. They are separate from categories.

#### 10. `tags`

| Column       | Data type    | Constraint              |
| ------------ | ------------ | ----------------------- |
| `id`         | BIGINT       | PK, identity            |
| `name`       | VARCHAR(100) | NOT NULL                |
| `slug`       | VARCHAR(120) | NOT NULL, UNIQUE        |
| `created_at` | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW() |

#### 11. `product_tags`

Connects products and tags. One product can have many tags, and one tag can belong to many products.

| Column       | Data type | Constraint                                            |
| ------------ | --------- | ----------------------------------------------------- |
| `product_id` | BIGINT    | PK (composite), FK → `products.id`, ON DELETE CASCADE |
| `tag_id`     | BIGINT    | PK (composite), FK → `tags.id`, ON DELETE CASCADE     |

The composite primary key is `(product_id, tag_id)`, which prevents duplicate assignments.

### D. Shopping cart

#### 12. `carts`

For this initial design, each customer has one cart.

| Column        | Data type   | Constraint                            |
| ------------- | ----------- | ------------------------------------- |
| `id`          | BIGINT      | PK, identity                          |
| `customer_id` | BIGINT      | NOT NULL, UNIQUE, FK → `customers.id` |
| `created_at`  | TIMESTAMPTZ | NOT NULL, DEFAULT NOW()               |
| `updated_at`  | TIMESTAMPTZ | NOT NULL, DEFAULT NOW()               |

#### 13. `cart_items`

| Column       | Data type   | Constraint                                               |
| ------------ | ----------- | -------------------------------------------------------- |
| `id`         | BIGINT      | PK, identity                                             |
| `cart_id`    | BIGINT      | NOT NULL, FK → `carts.id`, ON DELETE CASCADE             |
| `variant_id` | BIGINT      | NOT NULL, FK → `product_variants.id`, ON DELETE RESTRICT |
| `quantity`   | INTEGER     | NOT NULL, CHECK `quantity > 0`                           |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW()                                  |
| `updated_at` | TIMESTAMPTZ | NOT NULL, DEFAULT NOW()                                  |

Add `UNIQUE (cart_id, variant_id)` so the same variant appears only once per cart. Update its quantity instead of inserting a duplicate.

### E. Orders and checkout

#### 14. `orders`

Stores the order itself, including an address snapshot so later edits to the customer's address do not change an existing order.

| Column             | Data type     | Constraint                                                   |
| ------------------ | ------------- | ------------------------------------------------------------ |
| `id`               | BIGINT        | PK, identity                                                 |
| `order_number`     | VARCHAR(40)   | NOT NULL, UNIQUE                                             |
| `customer_id`      | BIGINT        | NOT NULL, FK → `customers.id`, ON DELETE RESTRICT            |
| `coupon_id`        | BIGINT        | NULL, FK → `coupons.id`, ON DELETE SET NULL                  |
| `status`           | VARCHAR(20)   | NOT NULL, DEFAULT `'pending'`, CHECK allowed order statuses  |
| `payment_status`   | VARCHAR(20)   | NOT NULL, DEFAULT `'unpaid'`, CHECK allowed payment statuses |
| `shipping_address` | JSONB         | NOT NULL                                                     |
| `billing_address`  | JSONB         | NULL                                                         |
| `subtotal`         | NUMERIC(12,2) | NOT NULL, CHECK `subtotal >= 0`                              |
| `discount_amount`  | NUMERIC(12,2) | NOT NULL, DEFAULT 0, CHECK `discount_amount >= 0`            |
| `shipping_fee`     | NUMERIC(12,2) | NOT NULL, DEFAULT 0, CHECK `shipping_fee >= 0`               |
| `tax_amount`       | NUMERIC(12,2) | NOT NULL, DEFAULT 0, CHECK `tax_amount >= 0`                 |
| `total_amount`     | NUMERIC(12,2) | NOT NULL, CHECK `total_amount >= 0`                          |
| `customer_note`    | TEXT          | NULL                                                         |
| `created_at`       | TIMESTAMPTZ   | NOT NULL, DEFAULT NOW()                                      |
| `updated_at`       | TIMESTAMPTZ   | NOT NULL, DEFAULT NOW()                                      |

Suggested order statuses: `pending`, `confirmed`, `processing`, `shipped`, `delivered`, `cancelled`, `returned`.

Suggested payment statuses: `unpaid`, `pending`, `paid`, `failed`, `partially_refunded`, `refunded`.

Keep these values consistent with your application. The final amount should be calculated and validated on the server, not trusted from the browser.

#### 15. `order_items`

Stores what was actually purchased. The snapshot columns preserve product details and prices even if the catalog changes later.

| Column               | Data type     | Constraint                                           |
| -------------------- | ------------- | ---------------------------------------------------- |
| `id`                 | BIGINT        | PK, identity                                         |
| `order_id`           | BIGINT        | NOT NULL, FK → `orders.id`, ON DELETE RESTRICT       |
| `product_id`         | BIGINT        | NOT NULL, FK → `products.id`, ON DELETE RESTRICT     |
| `variant_id`         | BIGINT        | NULL, FK → `product_variants.id`, ON DELETE SET NULL |
| `product_name`       | VARCHAR(200)  | NOT NULL                                             |
| `variant_attributes` | JSONB         | NOT NULL, DEFAULT `'{}'`                             |
| `sku`                | VARCHAR(100)  | NOT NULL                                             |
| `unit_price`         | NUMERIC(12,2) | NOT NULL, CHECK `unit_price >= 0`                    |
| `quantity`           | INTEGER       | NOT NULL, CHECK `quantity > 0`                       |
| `line_total`         | NUMERIC(12,2) | NOT NULL, CHECK `line_total >= 0`                    |
| `created_at`         | TIMESTAMPTZ   | NOT NULL, DEFAULT NOW()                              |

`line_total` should equal `unit_price × quantity`, with any item-level discounts handled consistently if you introduce them.

### F. Payments and stock management

#### 16. `payments`

One order can have multiple payment attempts, such as a failed attempt followed by a successful one.

| Column               | Data type     | Constraint                                                                         |
| -------------------- | ------------- | ---------------------------------------------------------------------------------- |
| `id`                 | BIGINT        | PK, identity                                                                       |
| `order_id`           | BIGINT        | NOT NULL, FK → `orders.id`, ON DELETE RESTRICT                                     |
| `provider`           | VARCHAR(50)   | NOT NULL, e.g. `cod`, `bkash`, `sslcommerz`                                        |
| `transaction_id`     | VARCHAR(150)  | NULL                                                                               |
| `amount`             | NUMERIC(12,2) | NOT NULL, CHECK `amount > 0`                                                       |
| `currency`           | CHAR(3)       | NOT NULL, DEFAULT `'BDT'`                                                          |
| `status`             | VARCHAR(20)   | NOT NULL, DEFAULT `'pending'`, CHECK `pending`, `successful`, `failed`, `refunded` |
| `provider_reference` | VARCHAR(150)  | NULL                                                                               |
| `provider_response`  | JSONB         | NULL                                                                               |
| `paid_at`            | TIMESTAMPTZ   | NULL                                                                               |
| `created_at`         | TIMESTAMPTZ   | NOT NULL, DEFAULT NOW()                                                            |
| `updated_at`         | TIMESTAMPTZ   | NOT NULL, DEFAULT NOW()                                                            |

Add a unique constraint on `(provider, transaction_id)` when transaction IDs are supplied, implemented as a partial unique index where `transaction_id IS NOT NULL`. Verify payment confirmations server-side with the payment provider.

For cash on delivery, record the payment attempt/status according to your chosen workflow. A successful online payment and a delivered COD order are not the same event.

#### 17. `inventory_transactions`

Keeps a history of stock increases, sales, returns, and manual corrections.

| Column             | Data type   | Constraint                                                      |
| ------------------ | ----------- | --------------------------------------------------------------- |
| `id`               | BIGINT      | PK, identity                                                    |
| `variant_id`       | BIGINT      | NOT NULL, FK → `product_variants.id`, ON DELETE RESTRICT        |
| `order_id`         | BIGINT      | NULL, FK → `orders.id`, ON DELETE RESTRICT                      |
| `transaction_type` | VARCHAR(20) | NOT NULL, CHECK `stock_in`, `stock_out`, `adjustment`, `return` |
| `quantity_change`  | INTEGER     | NOT NULL, CHECK `quantity_change <> 0`                          |
| `note`             | TEXT        | NULL                                                            |
| `created_at`       | TIMESTAMPTZ | NOT NULL, DEFAULT NOW()                                         |

Use positive quantities for stock additions and negative quantities for stock reductions. For `adjustment`, either sign is allowed.

`product_variants.stock_quantity` is the current stock balance; `inventory_transactions` is its audit history. Update the balance and insert the transaction together in a database transaction, preventing overselling during concurrent checkouts.

### G. Discounts

#### 18. `coupons`

| Column             | Data type     | Constraint                                         |
| ------------------ | ------------- | -------------------------------------------------- |
| `id`               | BIGINT        | PK, identity                                       |
| `code`             | VARCHAR(50)   | NOT NULL, UNIQUE                                   |
| `discount_type`    | VARCHAR(20)   | NOT NULL, CHECK `percentage` or `fixed`            |
| `discount_value`   | NUMERIC(12,2) | NOT NULL, CHECK `discount_value > 0`               |
| `max_discount`     | NUMERIC(12,2) | NULL, CHECK `max_discount > 0`                     |
| `min_order_amount` | NUMERIC(12,2) | NOT NULL, DEFAULT 0, CHECK `min_order_amount >= 0` |
| `usage_limit`      | INTEGER       | NULL, CHECK `usage_limit > 0`                      |
| `usage_count`      | INTEGER       | NOT NULL, DEFAULT 0, CHECK `usage_count >= 0`      |
| `starts_at`        | TIMESTAMPTZ   | NULL                                               |
| `expires_at`       | TIMESTAMPTZ   | NULL                                               |
| `is_active`        | BOOLEAN       | NOT NULL, DEFAULT TRUE                             |
| `created_at`       | TIMESTAMPTZ   | NOT NULL, DEFAULT NOW()                            |
| `updated_at`       | TIMESTAMPTZ   | NOT NULL, DEFAULT NOW()                            |

Additional rules:

- For `percentage`, `discount_value` must be at most `100`.
- If both dates are provided, `expires_at` must be later than `starts_at`.
- Enforce usage limits atomically during checkout to prevent concurrent orders from exceeding the limit.
- If you need per-customer usage limits, add a `coupon_redemptions` table later.

## 3. Complete relationship map

Here is how the tables connect to each other.

Account and customer

`users` 1 → 0..1 `customers`

`customers` 1 → many `addresses`

`users` 1 → 0..1 `email_verification_tokens`

`password_reset_tokens` is keyed by email and does not require a direct FK to `users`.

Product catalog

`categories` 1 → many `products`

`categories` 1 → many child `categories`

`products` 1 → many `product_variants`

`products` 1 → many `product_images`

`product_variants` 1 → many `product_images` (variant-specific images only)

`products` many ↔ many `tags`, through `product_tags`

Shopping and orders

`customers` 1 → 1 `carts`

`carts` 1 → many `cart_items`

`product_variants` 1 → many `cart_items`

`customers` 1 → many `orders`

`orders` 1 → many `order_items`

`product_variants` 1 → many `order_items` (historical variant reference)

`orders` 1 → many `payments`

`orders` 1 → many `inventory_transactions` (transactions associated with orders)

`product_variants` 1 → many `inventory_transactions`

`coupons` 1 → many `orders` (a coupon may be unused on an order)

## 4. Important database rules

Before implementing the migrations, make sure you account for these:

1. Index foreign keys and frequently queried fields. Examples include `addresses.customer_id`, `products.category_id`, `product_variants.product_id`, `product_images.product_id`, `cart_items.cart_id`, `orders.customer_id`, `order_items.order_id`, and `payments.order_id`. PostgreSQL does not automatically create indexes on the referencing side of every foreign key.
2. Use transactions for checkout. Validate prices, reserve or deduct stock, create the order and order items, and record stock movements atomically.
3. Protect historical orders. Do not hard-delete products or variants that have order history. Use archived/inactive status instead.
4. Keep order totals as snapshots. A later price change must not change an existing order's recorded price.
5. Validate status transitions in the application. For example, a cancelled order should not automatically become delivered without an explicit workflow.
6. Use secure authentication. Hash passwords and reset tokens, expire tokens, and rate-limit login and reset requests.

## 5. My final recommendation

This gives you 18 tables, including the optional tagging feature. If you want to launch with the fewest moving parts, you can initially omit `tags` and `product_tags` and add them when you need them.

Your media design remains straightforward:

- `users.avatar_path` — user profile image.
- `categories.image_path` — category thumbnail.
- `product_images` — product gallery and variant-specific images.
- `banners` — add later if you introduce promotional banners.

You do not need a general `media` table for this version. That is a valid design choice, not a database-design mistake.

One implementation note: this schema is a blueprint, not yet a complete migration script. The composite foreign key, partial unique indexes, discount rules, and a few cross-column constraints need to be explicitly implemented in PostgreSQL/Laravel migrations.
